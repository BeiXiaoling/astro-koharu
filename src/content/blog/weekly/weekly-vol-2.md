本周做了一件很基础的事：把构建耗时拆开看，确认哪一步在拖后腿。

## 拆解结果

首次构建总耗时 7 分 23 秒，其中：

| 阶段 | 耗时 | 说明 |
| :--- | ---: | :--- |
| 渲染页面 | 约 4 分钟 | 300 多页 Markdown 转 HTML |
| 图片优化 | 2 分 47 秒 | 108 张图转 avif/webp 多尺寸 |
| pagefind 索引 | 约 8 秒 | 全文搜索索引 |

真正的大头是图片。每张图要生成多个尺寸、两种格式，总计超过 400 个变体。

## 缓存的价值

第二次构建只用了 2 分 13 秒，因为图片全部命中缓存（日志里显示 `reused cache entry`），图片阶段从 2 分 47 秒降到 1.04 秒。

这意味着：**只要不改图片，日常写文章的构建成本其实只有 2 分钟左右**。之前担心的「改一句话等 8 分钟」，只会在新增或替换图片时出现。

## 一点体会

性能问题先别猜，把耗时按阶段列出来，答案通常很直接。这次如果不是拆开看，很容易误以为是 Astro 本身慢，从而做出错误的技术选型判断。

```bash
# 观察图片是否命中缓存
grep 'reused cache entry' /tmp/build*.log | wc -l
```
